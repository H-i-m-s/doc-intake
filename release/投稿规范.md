# 投稿规范

这份文件讲三件事：**用什么工具发**、**提交上去的格式长什么样**、**出错了怎么办**。
它是给人和 agent 看的，机器不读。

改市场规矩的时候，代码里对应的是 `release/market.mjs` 顶部那个 `MARKET` 常量块；这份文档跟着一起改。

---

## 一、工具与入口

| 入口 | 谁用 | 说明 |
| --- | --- | --- |
| `release\发布.cmd` | 你，双击 | 弹出窗口，选模式、填两行，按按钮 |
| `pwsh -NoProfile -STA -File release\ship.ps1` | 同上 | 窗口本身，`.cmd` 只是它的启动器 |
| `node release\publish.mjs --mode=…` | 我 / 命令行 | 同一个引擎，不带界面 |
| `node release\pack.mjs` | 只想要包 | 只出包，不管版本号和发布 |
| `node release\selfcheck.mjs` | 排错 | 只查这个插件的结构，不动任何东西 |

窗口和命令行走的是同一段代码，不存在两套逻辑。

## 二、三种模式

| 模式 | 做什么 | 出网 | 改你的仓库 |
| --- | --- | --- | --- |
| `pack` | 写版本号 + 出包到 `dist/` | 否 | 只改 `manifest.json` 的 version |
| `release` | pack + 提交打 tag 推送 + 在 GitHub 建 Release | 是 | 一次提交 + 一个 tag |
| `publish` | release + 向市场仓库开登记 PR | 是 | 同上，另外在你 fork 上落一个提交 |

阶段顺序是固定的：

```
配置 → 预检 → 写入版本号 → 出包 → 提交并打 tag → 发 Release → 投稿
```

版本号必须排在出包前面，因为 `<id>-v<version>.zip` 和 `app-<id>-<version>.entry.json`
这两个名字里都带着它。

## 三、市场规矩（硬约束）

这些对所有插件一样，写死在 `release/market.mjs` 的 `MARKET` 块里。

| 规矩 | 值 | 违反会怎样 |
| --- | --- | --- |
| 条目附件名 | `app-<id>-<version>.entry.json`（版本号前**没有** v） | 同步器找不到条目，整批失败 |
| 归档附件名 | `<id>-v<version>.zip`，由 entry 里的 `archive.url` 指名 | 附件对不上，整批失败 |
| entry 附件大小 | ≤ 512 KiB | 同步器读不下，整批失败 |
| tag 字符集 | `[A-Za-z0-9][A-Za-z0-9._+-]{0,127}` | 拒绝 |
| `approvals.json` 的 sha256 | 64 位小写十六进制，等于 zip 的 sha256 | 校验失败 |
| 版本方向 | 只能升，不能降；同一版本不能换包 | 拒绝 |
| 登记粒度 | 一个 PR 只登记一个扩展 | 维护者会退回 |

**发布之后不要动 Release 附件。** 客户端按批准的 sha256 校验下载，附件缺失或不一致会导致安装失败。

## 四、投稿改哪两个文件

市场那边全程走 GitHub API，**本地不留市场仓库的副本**。

- `registry.json`（名录）：只有第一次登记、或仓库/发布者变了才动。格式
  `{ "kind": "app", "id": "…", "repository": "owner/repo", "publisher": "…" }`。
- `approvals.json`（批准）：**每次都要动**。把这一个扩展的那行改成
  `{ "kind": "app", "id": "…", "tag": "v3.2.1", "sha256": "<zip 的 sha256>" }`。

其余规则：

- 别人的条目一个字都不碰，也不重排顺序。
- 2 空格缩进，文件结尾留一个换行。
- 分支固定叫 `enroll/<id>`，每次从正本最新提交重建，不做增量追加。所以它永远开在最新底座上。
- PR 标题：首次登记 `enroll: app/<id> v<版本>`，之后 `approve: app/<id> v<版本>`。
- PR 正文由脚本拼：图标和截图用仓库里的图片链接（`raw.githubusercontent.com`，钉在这个 tag 上），
  自测报告从 `release/自测.md` 渲染。那份文件是模板，里面的 `{{...}}` 由脚本填成这一版的真实数字，
  叙述部分写一次就够，不用每版重写。
- 截图是可选的。`release/pr-assets/` 里有图就自动列进正文，并跟着这次提交一起推上去；
  没有就写一行「本版未附截图」，不拦发布。只有自测报告是空的（`release/自测.md` 不存在或没内容）时，
  **PR 才开成 draft**；补齐后到网页上点一下 Ready for review 即可。

**为什么每次更新都要提 PR**：市场现在只认 `approvals.json` 里登记的"那一个包"，不认最新版。
它按登记的 tag 下载 zip、核对 sha256，对得上才放行。所以每发一版都要重新登记一次。

## 五、网络错误怎么办

原则一句话：**只重试"可能已经成功但没有收到回执"的那一类失败**；已经做好的部分不回滚，
只重跑没做完的阶段。

| 类别 | 长什么样 | 怎么处理 |
| --- | --- | --- |
| 瞬时网络 | `EOF`、`connection reset`、`Could not resolve host`、`timed out`、`502/503/504` | 脚本自己退避重试：最多 3 次尝试（失败后等 1s、4s）。每次都重新发请求，因为上一次可能其实已经成功 |
| 限速 | `API rate limit exceeded`、`secondary rate limit` | **不重试**。设一个只读的 `GITHUB_TOKEN` 环境变量，或等窗口过去再跑 |
| 认证失败 | `authentication failed`、`not logged in`、`401`、`Permission denied` | **不重试**。`gh auth login`，并确认账号对仓库有读写权限 |
| 事实错误 | sha256 不一致、tag 字符违规、条目超 512 KiB、版本倒退 | **不重试**。要你去改东西，日志会指名是哪一条 |
| 代理问题 | 上面几类反复出现、或只有某些域名失败 | 脚本不自己拼代理，跟着系统/gh 的代理设置走。失败时它会把实际生效的那一串原样打出来 |

跑的时候如果看到：

```
[警告] gh api 第 1 次失败（网络类），1 秒后重试：… EOF
```

这是正常的——它自己救回来了，不用管。

有一个例外是**发版前查远端 tag** 那一步：它不走“重试到通”，而是**必须问清楚**。三次都不通就停下，
不把“查不到”当成“远端没有这个 tag”——带着那个错觉往下走，会留下一个推不上去的 tag 和提交。

## 六、中途断了怎么办

每一步都是幂等的，**原样重跑同一个模式就行**：

- 包已经出好、Release 已经发出、PR 还没建 → 重跑 `publish`，它会跳过前两步，只提 PR。
- Release 已存在且两个附件和本地刚出的一致 → 跳过，不重复创建。
- Release 已存在但附件对不上 → 停下来报错，让你决定删掉重发还是换版本号。
- `approvals.json` 里已经是这个 tag + sha256 → 跳过提 PR。
- 分支已存在 → 直接把它更新到新提交，不追加、不冲突。

所以误按一次按钮不会出事。

## 七、出问题了从哪查

1. 先看日志最后那几行，脚本会把原因和"怎么办"一起打出来。
2. 结构问题（页面缺失、JS 语法错、manifest 字段缺）→ `node release/selfcheck.mjs`。
3. 包的内容不对 → `node release/pack.mjs`，看它列出多少条、sha256 是多少。
4. 想先看会做什么、不改任何东西 → 窗口里勾「干跑」。
5. 怀疑自己这条数据不对 → 窗口里勾「投稿前先复核一遍我的数据」，
   脚本会用市场自带的同步器重新下载你的 Release、重算 sha256，和你本地的比。
6. 市场那边合并后没生效 → 去看发布 Actions 有没有跑成功。合并本身不等于已上架。

## 八、换到别的插件

整个 `release/` 目录复制过去，放在插件根目录下（和 `manifest.json` 同级）。共享文件一个字都不用改，
每个插件各写各的只有三个：

| 文件 | 改什么 |
| --- | --- |
| `config.json` | `publisher`、`release.repo`、`pack.excludeDirs`（把那个插件自己的开发目录列进去，别忘了 `release` 自己）、`pack.selfcheck` |
| `selfcheck.mjs` | 按那个插件的结构重写；没有就删掉，并把 `pack.selfcheck` 改成 `"none"` |
| `自测.md` | 自测报告模板。占位符之外的叙述按那个插件的情况写一次，之后每版自动填数 |
| `pr-assets/` | 截图，可选。放进去就会被列进 PR 正文 |

`自测.md` 里能用的占位符（发布时由 `publish.mjs` 填）：

| 占位符 | 值 |
| --- | --- |
| `{{version}}` | 本次版本号 |
| `{{tag}}` | 本次 tag，形如 `v3.2.1` |
| `{{repo}}` | `config.release.repo` |
| `{{releaseUrl}}` | 这次 Release 的网页地址 |
| `{{date}}` | 发布当天（`YYYY-MM-DD`） |
| `{{hanaVersion}}` | 本机 Hana 版本，读 `HANA_HOME/last-update-version` |
| `{{os}}` | 本机系统与架构 |
| `{{sha256}}` / `{{sha256short}}` | 包的 sha256（完整 / 前 16 位） |
| `{{zipEntries}}` / `{{zipKiB}}` | 包里的条目数 / 大小 |
| `{{tests}}` / `{{jsfiles}}` | 单测用例数 / 语法检查过的文件数（都来自出包前那一次自检） |

写错的占位符会原样留在正文里，日志里会点名；某个值实在拿不到时留空，也会在日志里说一声，
免得你拿到一份带着空格的报告发出去。

搬完先跑 `node release/publish.mjs --mode=pack`，检查产物里的 id / name / 版本 / 图标是不是
刚复制的那个插件 —— 这一步能立刻暴露 config 抄漏了哪一项。

共享文件里不该出现任何插件名。见到就把那处改成通用的（比如调试用的环境变量别写死前缀）。
