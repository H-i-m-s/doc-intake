# 发版说明规范

发版时填的那段「这次改了什么」，就是这里的 Release 正文。它会被贴到两个地方：
GitHub Release 页面，和市场 PR 的正文。脚本用同一份文字，改一处两边都变。

---

## 一、正文写什么

只写用户在插件界面上能看到的变化。

判断一条该不该写，就问一句：装插件的人打开这个界面，会不会看到这一条说的东西？
看不到，删掉。

## 二、举个具体的

| 能写 | 不能写 |
| --- | --- |
| 长路径现在最多显示两行，两行装不下才在末尾省略 | `.file-name` 补上了 overflow:hidden |
| 长文件名不再压住右边的 +加/-减 数字 | 改用 class 建行时漏搬了 flex 那几条属性 |
| 状态徽标改为整行垂直居中 | 补了 align-self:center |

右边三句的问题一样：装插件的人不知道 `.file-name` 是什么，也不知道 `align-self` 是什么。
他读完只会觉得这段文字跟他没关系。

左边三句他读完能对上自己昨天看到的样子。

## 三、用小标题分组

正文按改动的类型分组，每组一个小标题，标题下面一条一行，前面加 `-`。

```
## 修复
- 长文件名不再压住右边的 +加/-减 数字
- 长路径现在最多显示两行，两行装不下才在末尾省略

## 新增
- 变更文件卡片顶部加了「详细」按钮
```

没有的那组直接不写。一次改动全是修 bug，就只留「修复」一组，不用为了对称硬凑一组空的。

不写安装步骤。脚本会自动在末尾补 `---` 和「安装：下载附件 zip 拖入 HanaAgent 设置 → 插件；或从市场更新」，自己再写一遍就重复了。

## 四、每条只讲一件事

一条讲一件事，别把三件事塞进一条。

## 五、不要写这些

- 改了哪个文件、哪个函数、哪个 CSS 属性、哪个 class
- 为什么坏、哪次改动弄坏的、漏了哪一行
- 用户看不见的东西：补测试、补光标样式、补点击区域、内部写法统一、两条路径对齐
- 踩过的坑、试了几次、绕了什么弯
- 下一版打算做什么

修 bug 只写修完之后的样子，不写为什么坏。

## 六、发布前自检

两条都过再发：

1. 每一条我都说得出用户在插件的哪一步会看到它？
2. 正文里有没有出现文件名、函数名、CSS 属性名、class 名？

有一条答不上，回去改。
